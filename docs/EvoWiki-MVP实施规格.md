# EvoWiki MVP 实施规格

## 问题陈述

研发文档主要由 AI Agent 生成，但当前团队没有一个受控、可审计的路径，把这些 Markdown 草稿交给人类核对后，发布为可由 AI 可靠检索的企业知识。完整产品愿景包含 Office 转换、飞书式评论、时光机、跨项目挂载和 LLM Wiki，但这些能力会阻塞最关键的验证：人工确认后的研发文档能否安全地版本化保存，并被 MCP 从原文中准确检索。

MVP 需要建立最小闭环：AI 能提交 Markdown 草稿，人类能审阅并发布，服务能将已发布文档提交到唯一 Git 文档仓库并建立原文 RAG 索引。未核对草稿、无权限项目和发布失败版本都不得被 MCP 检索。

## 方案

EvoWiki MVP 是一个单实例、自托管的 Markdown 发布与检索中枢。它使用单一企业 Git 文档仓库保存已发布 Markdown，使用本地 SQLite 保存用户、项目 ACL 与运行状态，并使用本地 ChromaDB 建立仅针对已发布原文的 RAG 索引。

MCP 使用调用者身份和项目 ACL 上传 `.md` 草稿。草稿保存于项目受控的待核对区域，不进入 Git、不进入向量索引。具备项目编辑权限的人在网页查看草稿、可作纯文本修订，再显式发布到正式文档区。发布服务串行执行精确路径 Git 提交、Git 推送和该文件的原文 RAG 索引；只有整个发布流程成功的版本可被 MCP 的读与检索工具返回。

## 用户故事

1. 作为系统管理员，我希望创建和管理项目及项目权限，以便每个项目都有明确的访问边界。
2. 作为系统管理员，我希望创建具有管理员权限的用户，以便自托管实例无需外部身份提供商即可运营。
3. 作为已授权的人类用户，我希望只浏览自己有权访问的项目，以便私有项目知识不会泄露。
4. 作为已授权的人类用户，我希望按需展开项目文档树，以便大型 Markdown 仓库仍然易用。
5. 作为持有用户 MCP 凭据的 AI Agent，我希望向已授权项目上传 Markdown 草稿，以便 AI 生成的文档可以进入人工核对。
6. 作为 AI Agent，我希望在权限不足、路径非法或文件不是 Markdown 时收到上传拒绝，以便修正请求而不暴露其他项目。
7. 作为审核人，我希望将项目中的待核对 AI 草稿与已发布文档分开查看，以便明确哪些文件尚不是可靠的 AI 知识。
8. 作为审核人，我希望预览待核对的 Markdown 草稿，以便依据领域知识核验 AI 输出。
9. 作为审核人，我希望在发布前以纯文本方式修订待核对草稿，以便小型事实或格式问题无需依赖另一套文档工具。
10. 作为审核人，我希望拒绝待核对草稿，以便不合适的 AI 输出绝不会进入 Git 仓库或 RAG 索引。
11. 作为审核人，我希望把已核对草稿发布到指定文档路径，以便它成为正式项目文档。
12. 作为审核人，我希望发布操作拒绝未明确确认的覆盖，以便 AI 输出不会静默替换既有文档。
13. 作为审核人，我希望看到发布处于待处理、已提交、已推送、已索引或失败状态，以便知道 AI 是否可以使用该文档。
14. 作为审核人，我希望能够重试失败发布，以便临时的 Git 远端或嵌入模型故障无需重新创建文档。
15. 作为已授权的 AI Agent，我希望只检索自己有权访问项目中的已发布文档，以便结果可作为企业知识使用。
16. 作为已授权的 AI Agent，我希望每个检索结果包含原始 Markdown 片段、文档路径和 Git commit，以便追溯到稳定来源。
17. 作为已授权的 AI Agent，我希望按路径和 commit 读取已发布文档，以便检查检索结果背后的原文。
18. 作为项目成员，我希望 AI 草稿、未索引文档和失败发布版本均不出现在 MCP 检索中，以便未完成方案不会被呈现为已批准知识。
19. 作为系统管理员，我希望所有文件写入都留在已授权项目根目录内，以便异常网页或 MCP 路径不能逃逸文档仓库。
20. 作为运维人员，我希望 Git 与索引工作串行执行，以便并发发布请求不会交错提交或破坏活动索引。
21. 作为运维人员，我希望 Git 推送或索引失败留下可见失败状态，而不是伪成功，以便明确恢复路径。
22. 作为人类阅读者，我希望 Markdown 和 Mermaid 文档安全渲染，且图表仅在手动展开后加载，以便文档可读且不会自动触发重型渲染。

## 实施决策

- MVP 是单个自托管实例，使用单一 `evowiki.db` SQLite 文件、一个 Git 文档仓库中的物理文件及本地 ChromaDB，不引入 MySQL 或 PostgreSQL。
- 发布是正式知识的唯一边界。待核对草稿只是运行输入；只有成功索引的 Markdown 才是 MCP 可使用的已发布知识。
- 系统设置一个高层的文档发布服务作为唯一 seam。网页发布及后续所有生产者都经过该服务；它负责鉴权、路径解析、精确文件 Git 暂存、推送、原文 RAG 索引、状态迁移和失败报告。
- MVP 中 MCP 提供 Markdown 草稿上传工具。它接收项目标识、安全相对目标名和 Markdown 内容，从 MCP 调用者继承权限；它不能直接发布、推送 Git 或索引内容。
- MCP 还提供只读检索与文档读取工具。工具仅检索调用者有权访问的项目，且只返回 Git 与原文 RAG 阶段均成功的发布记录。
- 人类 Markdown 上传可进入同一待核对流程，或明确标记为已核对内容；两条路径都必须经过同一发布服务，才能对 MCP 可见。
- 待核对草稿保存在项目受控的草稿区，不进入精确路径 Git 暂存或 ChromaDB。审核人可以预览、纯文本编辑、发布或拒绝草稿；富协同编辑不属于 MVP。
- 发布草稿必须指定目标文档路径。若目标路径已经发布，后端应拒绝操作，除非审核人明确确认替换。每次读写都必须解析绝对路径，并通过 `os.path.commonpath` 校验已授权项目根目录。
- MVP 的发布流程全局串行：暂存精确的已发布 Markdown 路径，创建单文件 Git commit，通过服务身份推送，然后替换或创建该文件的原文 RAG 条目。所有阶段成功前，请求不得报告成功。
- 失败阶段需要记录失败位置和原因。重试必须安全恢复发布；未发布或失败版本始终不可被 MCP 检索。推送失败后可保留本地 commit，但不得把它索引为已发布知识。
- 原文 RAG 使用确定性的 Markdown 切块：以标题结构为优先，不拆分代码围栏或表格，并记录文档路径、稳定标题上下文、片段标识和 Git commit 元数据。后端拥有切块边界的最终决定权。
- MVP 的嵌入模型配置属于部署配置，不提供模型配置 UI、reranking、LLM Wiki 编译或用户可配置 Endpoint。
- Web 门户使用 TypeScript 和按需加载的项目树。文档渲染采用 `react-markdown`；Mermaid 内容保持在人工展开的 `<details>` 中。
- SQLite 保留用户、项目权限和评论三张必需表。MVP 不开放评论流程，但评论与 Markdown 隔离的数据边界保持不变。
- MVP 不要求 WebSocket 通知。门户在自身操作成功或失败后刷新数据；未来若使用 WebSocket，只能发送 `REFRESH`。

## 测试决策

- 文档发布服务是主要测试 seam。测试应验证可观察契约：待核对草稿依 ACL 和路径校验被接受或拒绝；人类发布要么产生已提交、已推送、已索引的发布版本，要么产生精确失败状态。
- 测试使用临时文档仓库、SQLite 数据库、伪造 Git 执行器和伪造索引器，并在文档发布服务边界验证外部结果与记录状态，不测试私有辅助函数调用或框架接线。
- 安全测试覆盖路径穿越、绝对路径、适用时的符号链接逃逸、无权限项目、非 Markdown 上传，以及 MCP 直接发布尝试。
- 生命周期测试覆盖 AI 草稿上传、人类修订、拒绝、首次发布、明确替换、Git 失败、推送失败、索引失败、重试，以及所有不可用状态均不出现在 MCP 检索和文档读取中。
- 检索测试覆盖标题感知切块、代码围栏和表格完整性、来源元数据包含已发布 Git commit，以及在任何结果返回前完成 ACL 过滤。
- 前端测试覆盖可见行为：待核对与已发布列表分离，状态标签与后端结果一致，发布和重试操作正确，Mermaid 内容在展开前不渲染。
- 仓库当前没有实现或测试先例。首批测试在这个高层 seam 上定义行为，不建立按模块拆分的测试惯例。

## 不在范围内

MVP 不包含 Office/PDF/Excel 转换、MarkItDown、附件留底、Git LFS、原件预览和双栏转换校对。

MVP 不包含依赖挂载、共享项目树、跨项目检索，以及通过依赖传递 ACL。

MVP 不包含划词或盖楼评论、动态高亮、评论历史重建、Git 时光机 UI、差异查看、WebSocket 通知和多用户协同编辑。

MVP 不包含 MCP 直接发布、审核后的 MCP 文档修改、Agent 触发 Git push、LLM Wiki 编译、派生 Wiki 文档、reranking、模型配置 UI、长文档自动拆分和跨文档综合。

MVP 不包含高可用架构、多租户、外部关系型数据库、SSO、审计日志扩展、通知投递和自动数据保留工作流。

## 补充说明

- MVP 有意先建立原文 RAG 基线，再评估 LLM Wiki。在开始任何 LLM Wiki 工作前，团队应使用一小组可重复的真实研发问题与期望来源文档比较原文 RAG 的效果。
- MVP 之后的能力、进入条件和明确不采用的做法统一维护在[产品路线图](EvoWiki-产品路线图.md)；只有原文 RAG 的评估发现特定检索或综合问题后，才应进入 LLM Wiki。
- 现有完整 PRD 保留为产品愿景。规划首期实现时，以其 MVP 范围和本规格为准。
- 本规格已发布为 GitHub Issue #1，并应用 `ready-for-agent` 标签。
