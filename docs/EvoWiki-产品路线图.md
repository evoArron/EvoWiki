# EvoWiki 产品路线图

## 目的

本文记录 MVP 之外已经讨论并确认后置的能力，作为后续产品规划的唯一清单。路线图按验证门槛排序，不承诺日历日期：只有前一阶段的真实使用和评估满足门槛，才进入下一阶段。

具体工作项、阶段状态和优先级在 [GitHub Project：EvoWiki 路线图](https://github.com/users/evoArron/projects/1) 中跟踪；Project 不替代本文的阶段门槛和架构决策。

长期技术边界保持不变：单企业自托管、单实例、最多约 50 名活跃用户、单一企业 Git 文档仓库、SQLite `evowiki.db` 和物理文件路径。代码仓库与文档仓库始终分离；服务是 Git 的唯一推送者。

## 当前 MVP

**目标：** 验证“人工核对后的 AI Markdown 文档能否安全地版本化发布，并被 AI 从原文准确检索”。

- Markdown-only：人类或 MCP 仅提交 `.md` 文件。
- MCP 可上传待核对草稿；人类预览、纯文本修订、拒绝或显式发布。
- 已发布文件由服务串行完成精确路径 Git commit、Git push 和原文 RAG 索引。
- MCP 只读取已发布且已索引的原文，并返回路径与 Git commit。
- 保留 SQLite 用户与项目 ACL、JWT、`os.path.commonpath` 文件沙箱、按需加载文档树及 Mermaid 手动展开。
- 不把草稿、失败发布或待核对内容暴露给 MCP 检索。

**进入下一阶段的门槛：** 用至少 10 个脱敏的真实研发问题确认 Raw RAG 能命中正确原文、返回可追溯来源，并发现真实用户在审核或发布中遇到的首要阻塞点。

## 第一阶段：发布治理与审核协作

**目标：** 让团队可以安全地维护已发布知识，而不是只能一次性上传。

- 持久化并展示文件的待核对、已发布、已提交、已推送、已索引、失败和已撤回状态。
- 建立“已发布 source commit”与 RAG 索引版本的映射；新草稿不改变 AI 当前引用的已发布版本。
- 支持管理员紧急撤回 AI 发布：检索立即排除该文档，后台清理向量和派生产物，Git 原文和审计历史保留。
- 支持飞书式划词评论、楼层回复、Resolve/Reopen 和锚点失效提示。评论、选区快照和回复只存 SQLite，绝不写进 Markdown。
- 评论锚点保存文件路径、创建时 commit、选区文本、前后上下文和内容 hash；唯一匹配才高亮，歧义或失效时要求人工重新定位。
- MCP 在检索命中原文后可读取同一权限范围内的未解决关联评论；Resolved 评论默认不参与检索。
- 为评论、发布、撤回、权限变化、MCP 读写、附件下载和同步结果补充可追溯审计记录。

**进入下一阶段的门槛：** 团队能处理实际的审阅、评论、撤回和失败恢复，不会让草稿、已撤回内容或失效评论误导 AI。

## 第二阶段：文档资产与协作体验

**目标：** 降低既有企业资料入库和日常协作的成本。

- 支持 Word、Excel 和 PDF 上传；使用 MarkItDown 转换为 Markdown。
- 保留原始附件，提供原件与 Markdown 的双栏校对；Excel 的结构清洗与图片语义辅助必须由人类确认后才可发布。
- 为需要版本化的大附件接入 Git LFS，设置文件类型和大小上限。
- 提供 Git 时光机、历史 Markdown diff 和历史评论重现；历史评论由 SQLite 的追加事件与对应 commit 重建，而非复制 Markdown。
- 使用 WebSocket 仅广播项目 `REFRESH`；当前项目全量刷新，非当前项目仅显示状态提示，不传输流式文档文本。
- 允许 MCP 根据人类评论生成新的待核对 Markdown 草稿，但仍不得直接发布、推送或索引。
- 增加项目依赖挂载。依赖只声明候选知识源，不授予读取权限；用户必须同时拥有当前项目和依赖项目的权限。

**进入下一阶段的门槛：** Office/PDF 入库、附件版本和多项目知识浏览已经成为真实需求，并且 Git、SQLite 与原文 RAG 的运行状态可稳定恢复。

## 第三阶段：单文档 LLM Wiki 与增强检索

**目标：** 在 Raw RAG 基线上，验证单文档知识编译是否提高研发问题的检索质量。

- 仅系统管理员在界面配置嵌入、reranking 和编译模型档案；API Key 加密保存且不回显，Endpoint 仅允许安全的 HTTPS 外部服务并拒绝本机和私网地址。
- 管理员可为项目选择已启用模型档案；普通用户和项目管理员不可填写 Endpoint 或 Key。
- 每个已发布原文 commit 可生成只读的 `.llm-wiki/` 派生 Markdown，并形成独立的机器 Git commit。原始 Markdown 始终是唯一事实来源。
- 派生页记录原文路径、原文 commit、内容 hash、模型档案、prompt 版本、生成时间和状态，并包含文档摘要、术语/缩写、关键约束、章节导航、待确认项与来源区。
- LLM 只读取已发布的干净 Markdown，不读取附件原件、SQLite 评论、草稿、其他项目或依赖项目内容。
- 检索采用 Wiki-first：优先检索已发布且校验通过的派生页，再回到关联原文 chunk；没有派生命中、证据不足、派生过期或编译失败时自动回退 Raw RAG。
- 每个派生段落必须能映射到原文路径、source commit 和 chunk/范围。服务端校验失败时拒绝激活派生内容，不创建活动增强索引。
- 不展示或依赖模型自评的“可信度”。仅展示可机械验证的来源、编译配置、版本和人类发布状态；未来的人类审核可独立标记“已验证”。
- 模型、prompt 或 chunk 规则变化会使派生结果过期。系统继续以 Raw RAG 服务，管理员可启动项目级串行重编译。
- 同一文件有更新发布版本时，尚未开始的旧编译任务取消；已开始的旧任务即使完成也不得成为活动索引。

**进入下一阶段的门槛：** 使用 30-50 个脱敏的真实问题，对比 Raw RAG 与编译增强 RAG 的正确率、原文引用完整性、无答案拒答质量、延迟、token 使用量和入库成本。只有跨文档或长文档问题存在稳定收益，才进入完整知识编译。

## 第四阶段：跨文档知识编译与规模化维护

**目标：** 将经过验证的 LLM Wiki 从单文档增强扩展为可审计的跨文档知识层。

- 对超出模型有效输入预算的文档自动拆分，执行分段摘要、文档摘要和层级综合；保留每一层对原文的来源引用。
- 生成跨文档的概念页、实体页、比较页、项目概览、冲突说明和导航索引；这些页面均为只读派生产物，不与人类原文混写。
- 维护 source 影响图，按源文件更新范围选择性重编译，避免每次变更全项目重算。
- 为派生知识加入陈旧、冲突、孤儿来源、缺失引用和未编译覆盖率的 lint 与维护报告；lint 发现问题，不自动改写已发布知识。
- 支持大数据、远程数据和二进制资料的 manifest、样本和查询配方，不把不适合 Markdown 的内容强行复制为大文本。
- 对 ACL 变化、发布撤回、源文件删除和保留期到期，在原文、派生页、向量索引、缓存和历史查询中统一执行不可见处理。

## 远期运营能力

- 企业 SSO、密码策略、账户生命周期与更细的管理员操作审计。
- 备份、恢复演练、灾难恢复目标和附件/SQLite/Git 一致性检查。
- 更丰富的通知策略、失败告警、队列观测、成本统计和索引健康面板。
- 高可用、横向扩展或多租户仅在单实例上限被实际验证突破后评估；在此之前不引入外部关系型数据库。

## 明确不采用的做法

- 人类、MCP 或外部系统直接向受保护分支 Git push；只有 EvoWiki 服务身份可推送。
- 将评论、高亮、AI 生成标记或运行状态写进干净的 Markdown 原文。
- 将代码仓库纳入 EvoWiki 的写入、提交或回滚范围。
- 在未建立 Raw RAG 基线和评测集前，宣称 LLM Wiki 必然提升召回或取代检索。
- 以模型自评置信度代替人类审核或原文来源证据。
